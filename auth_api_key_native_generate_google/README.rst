This module adds an HTTP endpoint that exchanges a **Google ID token**,
obtained by a native app (Android Credential Manager, iOS GIDSignIn,
``google_sign_in`` in Flutter), for a native Odoo API key
(``res.users.apikeys``).

It extends ``auth_api_key_native_generate``, which does the same
exchange from a login and a password. The key, its ``rpc`` scope, its
validity window and the response shape are the same, so a client can
switch between both exchanges without changing how it uses the key. The
user never types an Odoo password.

-  The token is verified on the server against Google's public keys:
   RS256 signature, issuer, audience (the configured client IDs),
   expiry, freshness and verified email.
-  Only accounts of the configured Google Workspace domains are
   accepted. The ``hd`` claim and the email domain must both match
   exactly.
-  The Google account must match one existing, active, internal user, by
   login first, then by email. No user is ever created.
-  Each device gets its own key, replaced when the same device signs in
   again.

Stock ``auth_oauth`` doesn't fit this case: it is built for the browser
redirect flow, validates an OAuth access token and opens a web session,
while a native app holds an ID token and needs an API key.

Configuration
=============

Go to **Settings > General Settings > Integrations > Google Sign-in for
API Keys**:

-  **Google Client IDs**: the OAuth client IDs accepted as the token
   audience, comma-separated. On Android the token is issued for the
   **web** client ID (the app's ``serverClientId``), on iOS for the
   **iOS** client ID, so this is usually both. Empty (the default)
   disables the route: it answers ``404``, as if the module were not
   installed.
-  **Allowed Workspace Domains**: lower-case, comma-separated, e.g.
   ``example.com``. Required when client IDs are set.
-  **Maximum Token Age** (default ``600`` seconds, ``60`` to ``3600``):
   tokens issued longer ago are refused as stale.
-  **Allow Two-Factor Users** (default on): users with Odoo two-factor
   authentication get a key through this route, relying on Google's
   2-step verification instead. Turn it off to refuse them, as the
   password route does.
-  **Key Name Prefix** (default ``Google sign-in``): issued keys are
   named ``<prefix> (<device name>)``.
-  **Maximum Keys per User** (default ``10``, ``1`` to ``100``): beyond
   that number of keys named after the prefix, issuing a new one removes
   the oldest.

The key validity is the base module's setting. The values are stored as
``auth_api_key_native_generate_google.*`` system parameters. A value
that can't be read at request time (edited directly in the system
parameters) disables the route and logs an error; it never falls back to
accepting any client ID or domain.

No client secret is needed: client IDs aren't secrets, and the token is
verified locally, without calling Google's token endpoint.

In the Google Cloud project of the Workspace, set the OAuth consent
screen to *Internal*, so that Google itself refuses accounts from
outside the organization. This module remains the authoritative check.

Reverse proxy
-------------

-  Rate-limit ``/api/auth/google/generate_api_key``. There is no secret
   to guess, so Odoo's login cooldown doesn't apply. Allow a whole
   office signing in from one NAT IP (e.g. 30 requests per minute per
   IP).
-  Do not put HTTP Basic Authentication in front of this route or
   ``/json/2``: the app sends its API key in the ``Authorization``
   header, and Basic credentials shipped inside a distributed app
   protect nothing.
-  Enable proxy mode, so that client IPs in the logs are accurate.

Usage
=====

Request a key by POSTing the Google ID token to the endpoint:

::

   POST /api/auth/google/generate_api_key
   Content-Type: application/json

   {
     "db": "mydb",
     "id_token": "eyJhbGciOiJSUzI1NiIs...",
     "device_name": "Pixel 8"
   }

``device_name`` is optional (64 characters at most). Each device should
send a stable name that is unique for the user, for instance the device
model plus a short identifier generated once per install
(``Pixel 8 · 3f9a``): a sign-in replaces the user's key with the same
name. Without a device name, no key is replaced.

On success (HTTP 200) the response holds the key, its expiration date
(ISO 8601, UTC) and the matched user:

.. code:: json

   {
     "api_key": "0123456789abcdef...",
     "expiration_date": "2027-01-19T08:00:00+00:00",
     "user": { "id": 42, "login": "jane@example.com", "name": "Jane Doe" }
   }

Use the key as the bearer credential for ``/json/2``:

::

   curl -H "Authorization: Bearer 0123456789abcdef..." \
        https://mydb.example.com/json/2/...

The key is listed in the user's preferences, under *Account Security >
API Keys*, where it can be revoked. Archiving the user, removing the key
or reaching its expiration date invalidates it.

Error responses hold a human readable ``error`` and a stable ``code``.
Clients map on ``code``:

+--------+------------------+------------------+------------------+
| Status | ``code``         | When             | Suggested client |
|        |                  |                  | behaviour        |
+========+==================+==================+==================+
| 400    | ``i              | malformed body,  | "sign-in failed" |
|        | nvalid_request`` | bad ``id_token`` |                  |
|        |                  | characters       |                  |
+--------+------------------+------------------+------------------+
| 401    | `                | signature,       | sign out of      |
|        | `invalid_token`` | algorithm, key,  | Google, "sign-in |
|        |                  | audience,        | failed"          |
|        |                  | issuer, expiry,  |                  |
|        |                  | missing claims   |                  |
+--------+------------------+------------------+------------------+
| 401    | ``stale_token``  | token older than | get a fresh      |
|        |                  | the maximum age  | token            |
|        |                  |                  | interactively,   |
|        |                  |                  | retry once       |
+--------+------------------+------------------+------------------+
| 403    | ``em             | email not        | sign out of      |
|        | ail_unverified`` | verified         | Google, "sign-in |
|        |                  |                  | failed"          |
+--------+------------------+------------------+------------------+
| 403    | ``wrong_domain`` | account outside  | sign out of      |
|        |                  | of the allowed   | Google, "use     |
|        |                  | domains          | your company     |
|        |                  |                  | account"         |
+--------+------------------+------------------+------------------+
| 403    | ``no_user``      | no single active | sign out of      |
|        |                  | internal user    | Google, "no Odoo |
|        |                  | matches          | user, contact an |
|        |                  |                  | admin"           |
+--------+------------------+------------------+------------------+
| 403    | ``mfa_enabled``  | two-factor user, | "sign in with a  |
|        |                  | and they are not | password"        |
|        |                  | allowed          |                  |
+--------+------------------+------------------+------------------+
| 404    | ``not_found``    | unknown          | "sign-in failed" |
|        |                  | database, or     |                  |
|        |                  | route not        |                  |
|        |                  | configured       |                  |
+--------+------------------+------------------+------------------+
| 413    | (no JSON body)   | body over 8 KiB  | "sign-in failed" |
+--------+------------------+------------------+------------------+
| 503    | ``goog           | Google's keys    | "try again",     |
|        | le_unavailable`` | can't be fetched | keep any         |

A ``stale_token`` typically comes from a cached token, e.g. returned by
``attemptLightweightAuthentication()`` in ``google_sign_in``: the client
should request a fresh one, and must not sign the user out of Google.

The user is matched on the verified Google email, exactly and
case-insensitively: on ``login`` first, then on ``email`` when no login
matches. The Workspace primary address must be stored in one of them;
aliases are not resolved. Several matches are refused as ambiguous.

Nonces are not used: ``google_sign_in`` accepts a nonce only once per
app launch. Replay is limited by TLS and the maximum token age, and a
replayed token gives nothing the same Google account couldn't get by
signing in again.
